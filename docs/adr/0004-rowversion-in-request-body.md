# 0004 – Optimistic Concurrency עם `rowVersion` בגוף הבקשה

**סטטוס:** התקבלה · 03/11/2026

## הקשר
כמה משתמשים עובדים על אותן פניות. משתמש פותח פנייה, ובזמן שהוא מחליט, משתמש אחר משנה את הסטטוס שלה. בלי הגנה, העדכון השני דורס את הראשון בשקט, וההיסטוריה מתעדת מעבר שלא קרה מהסטטוס שהמשתמש ראה.

## החלטה
- לכל פנייה עמודת `rowversion` של SQL Server, שמשתנה לבד בכל עדכון.
- הלקוח שולח בגוף ה-`PATCH` את הגרסה שהוא ראה (`{ status, rowVersion }`, ב-Base64).
- השרת בודק את הגרסה לפני בדיקת המעבר, ו-EF Core כולל אותה גם ב-`WHERE` של ה-`UPDATE`. כך נתפס גם עדכון שקרה בין הקריאה לכתיבה. במקרה כזה `DbUpdateConcurrencyException` הופך ל-409.
- תשובת 409 כוללת את המצב העדכני של הפנייה (`current`), כולל המעברים המותרים ממנו. הממשק מציג אותו מיד ומציע לנסות שוב רק אם המעבר עדיין חוקי.
- שינוי הסטטוס ושורת ההיסטוריה נשמרים ב-`SaveChanges` אחד, כלומר בטרנזקציה אחת.

## חלופות שנשקלו
- **`If-Match` עם ETag:** הדרך התקנית ב-HTTP. נדחתה כי ב-Bulk יש גרסה לכל פריט, ואין לה מקום בכותרת אחת. גרסה בגוף הבקשה היא צורה אחת לשני ה-Endpoints.
- **נעילה פסימית** (`UPDLOCK` בזמן שהמשתמש מחליט): מחזיקה נעילות לאורך זמן אנושי, ולא מתאימה ל-API בלי מצב.
- **Last write wins:** פשוט, אבל מאבד עדכונים בלי שאף אחד יודע.

## השלכות
- `rowVersion` חובה בבקשה. בקשה בלעדיו נדחית ב-400.
- הבדיקה `ConcurrencyTests` שולחת עשרה עדכונים מתחרים לאותה פנייה: אחד מקבל 200, תשעה 409, ונשמרת שורת היסטוריה אחת. כשבדיקת הגרסה הוסרה זמנית, הבדיקה נכשלה.
- `RaceInjector` (בבדיקות בלבד) מכריח את המרוץ בין הקריאה לכתיבה, כדי שהמקרה הנדיר ייבדק בכל הרצה.
