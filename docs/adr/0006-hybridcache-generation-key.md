# 0006 – HybridCache עם מספר דור (Generation Key)

**סטטוס:** התקבלה · 03/11/2026

## הקשר
הסיכום (כמה פניות בכל סטטוס ובכל עדכון) נטען בכל כניסה למסך הרשימה. בלי סינון הוא סופר את כל הטבלה, וזה החישוב היקר ביותר במערכת. הנתונים משתנים בכל עדכון סטטוס, כך שה-Cache חייב להתעדכן, ולא להחזיר מספרים ישנים.

## החלטה
- **רק הסיכום בלי סינון נשמר.** סיכומים מסוננים מחושבים בכל בקשה: יש אינסוף צירופי סינון, והסיכוי לפגוע באותו צירוף נמוך.
- **HybridCache** של ‎.NET: כשהערך חסר והרבה בקשות מגיעות יחד, החישוב רץ פעם אחת (הגנה מ-Stampede).
- **מספר דור במפתח** (`summary:v{n}`): כל עדכון סטטוס מעלה את המספר (`Interlocked.Increment`) אחרי שהשמירה הצליחה. חישוב שהתחיל לפני העדכון ומסתיים אחריו נכתב תחת הדור הקודם, שאף אחד כבר לא קורא.
- **TTL** של 60 שניות (`Cache:SummaryTtlSeconds`) כרשת ביטחון.

## חלופות שנשקלו
- **מחיקת המפתח בכל עדכון:** לא מספיקה. חישוב איטי שהתחיל לפני העדכון כותב את הנתון הישן בחזרה אחרי המחיקה.
- **`IMemoryCache` עם נעילה ידנית:** אותה תוצאה עם יותר קוד, ובלי מעבר פשוט ל-Redis.
- **בלי Cache:** פשוט, אבל הסיכום הוא השאילתה הכי יקרה, והיא רצה בכל טעינת מסך.

## השלכות
- במופע אחד, בזיכרון. בכמה מופעים כל מופע מחזיק דור משלו. המעבר: Redis כשכבה שנייה של HybridCache (שינוי הגדרה), ומונה הדור ב-Redis (`INCR`), כדי שכל המופעים יראו אותו דור.
- `SummaryCacheTests` מכריח את המרוץ בין חישוב לעדכון. כשמספר הדור הוסר זמנית מהמפתח, הבדיקה נכשלה.
- נמדד: סיכום מה-Cache כ-1ms דרך ה-API, לעומת כ-16ms CPU לחישוב ([PERFORMANCE.md](../PERFORMANCE.md)).
