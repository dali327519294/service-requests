# שימוש בכלי AI

הפרויקט פותח בעזרת **Claude Code** (Anthropic, מודל Claude Opus 5.5), שעובד ישירות בתיקיית הפרויקט.
המסמך מתעדכן בסוף כל משימה.

## איך עבדנו
- **הכלי כותב, אני מחליטה ובודקת.** כל קוד מוצג לי ומוסבר לפני שהוא נכתב, ואני עוברת על כל PR לפני Merge.
- **TDD:** בכל לוגיקה עסקית, הבדיקה נכתבת ונכשלת לפני הקוד.
- **Push, PR ו-Merge נעשים רק על ידי.** כל commit שהכלי השתתף בו מסומן ב-`Co-Authored-By`.
- **ניהול מידע רגיש:** מפתחות, סיסמאות ומחרוזות התחברות אינם נשמרים ב-Repository. בסביבת הפיתוח הם מנוהלים ב-User Secrets, וב-CI ב-GitHub Secrets.

## לפי משימה
| משימה | מה הכלי עשה | מה החלטתי | מה בדקתי |
|---|---|---|---|
| תכנון | ניתוח הדרישות, הצגת חלופות לכל החלטה, ניסוח האפיון והתוכנית | כל החלטה טכנולוגית, אחת-אחת; סדר העבודה; לוח זמנים של 5 ימים | קראתי ואישרתי את האפיון והתוכנית לפני שהתחלנו לכתוב קוד |
| 1 – שלד | יצירת הפתרון, הגדרות Build, תבניות, סקריפט הקמה ל-GitHub | שם ה-Repository, Repository ציבורי, לוח Kanban | הרצתי את הסקריפט ובדקתי את ה-Issues והלוח |
| 2 – CI | Workflow עם SQL Server ב-Container | ש-CI ירוק יהיה תנאי ל-Merge (Ruleset) | ראיתי את ה-CI רץ על ה-PR |
| 3 – Domain | ישויות ומעברי סטטוס ב-TDD | סדר העבודה ב-Review: קודם הערה ב-PR, אחר כך תיקון | כתבתי הערות Review על ה-PR לפני התיקונים |

## החלטות שבהן שיניתי את ההמלצה
| הכלי הציע | החלטתי | למה |
|---|---|---|
| Cache בסיסי | HybridCache עם Generation Key | Cache פשוט מדי לא מטפל בבעיה האמיתית: נתונים לא עדכניים אחרי עדכון |
| להוציא את האימות וההרשאות מההיקף | בלוק מותנה, עם נקודת החלטה בסוף יום 3 | אימות והרשאות הם דרישת אבטחה בסיסית במערכת ארגונית; עדיף לתכנן אותם ולהכריע לפי ההתקדמות בפועל מאשר לוותר עליהם מראש |
| לוח זמנים של 6 ימים | 5 ימים, עד 05/11 | התאמה למועד ההגשה האמיתי |
| למחוק את הלו"ז הישן מההיסטוריה | להשאיר ולהוסיף commit | שכתוב היסטוריה מסוכן ומסתיר את תהליך העבודה |
| תיקון ואז הערה ב-PR | קודם הערה ב-PR, אחר כך commit שמתקן | כך ה-Review מתעד את הבעיה לפני הפתרון |
