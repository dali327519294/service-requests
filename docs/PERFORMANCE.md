# ביצועים: מדידה, אינדקסים וצווארי בקבוק

המסמך מתעד איך נמדדו השאילתות של המערכת על 100,000 פניות, מה נמצא, מה תוקן ומה נשאר כמגבלה ידועה.
כל המספרים כאן נמדדו בפועל ואפשר לחזור עליהם (ראו "איך להריץ שוב" בסוף).

## סיכום

- **הממצא העיקרי:** דף הרשימה, התצוגה שכל משתמש פותח, לא השתמש באינדקס. כל עמוד של 20 פניות קרא את כל 100,000 השורות (1,879 דפים) ומיין אותן.
- **הסיבה:** השאילתה ממיינת לפי `CreatedAt` ואחר כך לפי `Id` כשובר שוויון, באותו כיוון. באינדקס, ש-SQL Server מוסיף לסופו את המפתח הראשי בסדר עולה, הסדר לא תאם.
- **התיקון:** `Id` נוסף למפתח של שני אינדקסי הרשימה, באותו כיוון כמו התאריך (Migration `MatchListIndexesToSortOrder`).
- **התוצאה:** העמוד הראשון ירד מ-2,092 קריאות ל-278, וסינון לפי סטטוס מ-1,918 ל-103. זמן ה-CPU ירד מעשרות מילישניות ל-0.
- **תופעת לוואי שנמצאה במדידה נוספת ותוקנה:** אחרי התיקון, חיפוש עם מעט התאמות הלך לפי אינדקס התאריכים ובדק כמעט כל שורה (עד 298,776 קריאות). כשההתאמות מעטות ביחס לעמוד, החיפוש קורא עכשיו את הטבלה פעם אחת (1,881 קריאות). ראו "חיפוש עם מעט התאמות".
- **מגבלה שנשארה:** חיפוש חופשי (`LIKE '%מילה%'`) בודק את כל השורות כדי לספור אותן, כ-170–250ms לבקשה. הצעת שיפור מופיעה בסוף.

## שיטה

| שלב | איך |
|---|---|

| הרצה כמו ב-EF | כל שאילתה רצה דרך `sp_executesql` עם פרמטרים מטיפוסים זהים, כך ש-SQL Server בונה לה אותה תוכנית |
| מדדים | `SET STATISTICS IO, TIME` (דפים שנקראו, CPU, זמן כולל) ו-`SET STATISTICS XML` (תוכנית הריצה בפועל) |
| חזרות | הרצה אחת לחימום, ואז 5 הרצות. הזמן הוא החציון. כל הקריאות מהזיכרון (logical reads) |
| "בלי אינדקסים" | אותה שאילתה עם `WITH (INDEX(1))`, שמכריח סריקה של הטבלה כולה. לא נמחק שום אינדקס |
| תוכניות ריצה | ארבע התוכניות שמוכיחות את הממצא המרכזי נשמרו ב-[`performance/plans/`](performance/plans) (ראו מתחת לטבלת לפני/אחרי). את כל השאר הסקריפט מייצר מחדש |
| סביבה | SQL Server LocalDB, 100,000 פניות מה-Seed, מחשב פיתוח |

המדד המרכזי הוא **logical reads**: כמה דפים של 8KB SQL Server קרא. הוא לא תלוי בעומס על המחשב, ולכן הוא המדד הכי יציב להשוואה. זמני ה-CPU מוצגים לצדו.

## חיפוש עם מעט התאמות

**הממצא:** אחרי תיקון האינדקסים, הרחבנו את המדידה ממילה נפוצה למילים נדירות. חיפוש טקסט (`LIKE '%מילה%'`) הוא תנאי ש-SQL Server לא יודע להעריך, ולכן הוא תמיד בוחר ללכת לפי אינדקס התאריכים ולבדוק שורה אחרי שורה עד שהעמוד מתמלא. כשיש הרבה התאמות זה מהיר. כשיש מעט התאמות ביחס לשורות שהעמוד צריך, הוא עובר כמעט על כל הטבלה, עם קפיצה לטבלה לכל שורה.

**התיקון:** ה-API כבר סופר את ההתאמות לפני שהוא מביא את העמוד. כשיש פחות מ-2 התאמות לכל שורה שהעמוד צריך, שאילתת העמוד קוראת את הטבלה פעם אחת וממיינת רק את מה שנמצא (`SearchPlan` ב-`RequestQueryService`). סינונים אחרים (סטטוס, ארגון, תאריכים) לא מושפעים, כי SQL Server מעריך אותם נכון.

**איך נקבע הסף:** אותה שאילתת עמוד, מילה עם 90 התאמות, עמודים שונים:

| התאמות לכל שורה שהעמוד צריך | לפי אינדקס התאריכים | קריאה אחת של הטבלה |
|---|---|---|
| 1 (עמוד שצריך שורות 71–90) | 298,776 · 344ms | **1,881 · 188ms** |
| 1.5 (שורות 41–60) | 212,722 · 219ms | **1,881** · 235ms |
| 4.5 (שורות 1–20) | 89,498 · **109ms** | **1,881** · 188ms |
| 22 (443 התאמות, שורות 1–20) | 12,681 · **0ms** | 1,881 · 203ms |
| 119 (2,370 התאמות) | **1,249 · 0ms** | 1,881 · 203ms |

(בכל תא: דפים שנקראו · זמן CPU חציוני)

קריאת הטבלה עולה תמיד כ-1,881 דפים וכ-200ms של CPU, כי `LIKE` נבדק על כל 100,000 השורות. מתחת ל-2 התאמות לשורה היא טובה יותר בשני המדדים, ולכן זה הסף. מעליו אינדקס התאריכים עולה פחות CPU. מספר הקריאות שלו גבוה, אבל אלה ביקורים חוזרים בדפים שכבר בזיכרון (כל הטבלה היא 1,879 דפים), ולכן נבדק גם זמן התגובה: סף של 5 נוסה ונדחה, כי בעמוד הראשון של מילה עם 90 התאמות הוא העלה את זמן התגובה דרך ה-API מ-329ms ל-431ms (ממוצע של 20 קריאות).

**ההוכחה בתוכניות הריצה:** [לפני התיקון: Index Scan של 97,492 שורות, וקפיצה לטבלה לכל אחת](performance/plans/rare-search-before-fix.sqlplan) · [אחרי התיקון: Clustered Index Scan, ו-Sort של 90 שורות](performance/plans/rare-search-after-fix.sqlplan).

הבדיקות `SearchPlanTests` (הסף והגבולות שלו) ו-`A_rare_search_reads_the_table_once_and_still_pages_newest_first` (התוצאות, הסדר וה-SQL שנשלח) מגינות על ההתנהגות.

## איך נמנעת טעינה לזיכרון

- **דפדוף בשרת:** כל עמוד הוא `OFFSET ... FETCH NEXT 20`, ורק 20 שורות עוברות מבסיס הנתונים ל-API.
- **הסינון והמיון ב-SQL:** כל התנאים נבנים כ-`IQueryable` ומתורגמים ל-`WHERE` ו-`ORDER BY`. שום רשימה לא מסוננת בזיכרון.
- **הסיכום ב-SQL:** הספירה לפי סטטוס ולפי עדיפות היא `GROUP BY` בשרת. מגיעות 4 ו-3 שורות, לא 100,000.
- **בלי מעקב שינויים בקריאה:** שאילתות הקריאה הן `AsNoTracking` ומחזירות DTO, בלי ישויות שנשמרות ב-DbContext.
- **Cache לסיכום בלי סינון:** HybridCache עם מפתח דור שמתחלף בכל עדכון, ולכן 1.1ms במקום 16ms.
- **Bulk מוגבל:** עד 100 פניות בבקשה אחת.

## האינדקסים ולמה כל אחד קיים

| אינדקס | מפתח | משרת |
|---|---|---|
| `IX_Requests_CreatedAt` | `CreatedAt DESC, Id DESC` | הרשימה בלי סינון, בשני כיווני המיון (קריאה לאחור הופכת את שני הכיוונים יחד) וסינון טווח תאריכים |
| `IX_Requests_Status_CreatedAt` | `Status, CreatedAt DESC, Id DESC` + `INCLUDE (Priority)` | סינון לפי סטטוס, והסיכום: הספירות לפי סטטוס ולפי עדיפות נקראות מהאינדקס הצר בלי לחזור לטבלה |
| `IX_Requests_OrganizationName` | `OrganizationName` | סינון "שם הארגון מתחיל ב" (`LIKE 'x%'` הוא Seek) ומיון לפי ארגון |
| `IX_Requests_AssignedTo_Status` | `AssignedTo, Status` | סינון לפי מטפל |
| `IX_RequestStatusHistory_RequestId_ChangedAt` | `RequestId, ChangedAt DESC` | היסטוריה של פנייה אחת |

**למה `Id` חייב להיות במפתח:** כל מיון ברשימה מסתיים ב-`Id` באותו כיוון, כדי ששורות עם אותו תאריך לא יופיעו בשני עמודים או באף אחד. אינדקס מחזיר שורות ממוינות רק אם הסדר שלו תואם בדיוק. כש-`Id` לא מוגדר, SQL Server מוסיף אותו לסוף בסדר עולה. אז `CreatedAt DESC, Id DESC` לא תואם, וגם בקריאה לאחור לא: הסדר שמתקבל הוא `CreatedAt ASC, Id DESC`. הבדיקה `Indexes_match_the_spec` מוודאת את המבנה הזה.

**פיצול (Fragmentation) אחרי ה-Seed:** המפתח הראשי 0.1%, `IX_Requests_AssignedTo_Status` 2.3%, `IX_Requests_OrganizationName` 0%, והדפים מלאים ב-98.6–99.6%. ה-Seed מכניס את השורות בסדר המפתח, ולכן אין פיצול שדורש Rebuild. שני אינדקסי הרשימה נבנו מחדש ב-`MatchListIndexesToSortOrder` לפני המדידה, ולכן ה-0–1.7% שלהם לא מעיד על ה-Seed.

**Filtered Index (`WHERE Status <> 4`), נבדק ולא נוסף.** ההשערה הייתה שאינדקס רק על פניות שלא הושלמו (65% מהשורות) יחסוך קריאות. אבל אף שאילתה במערכת לא מסננת "הכל חוץ מהושלמו":
- סינון לפי סטטוס כבר עושה Seek ל-103 דפים.
- הסיכום חייב לספור גם את הפניות שהושלמו.
- הרשימה כברירת מחדל כוללת את כל הסטטוסים.

אינדקס כזה היה מוסיף עלות לכל עדכון, בלי לשרת אף שאילתה.

## איך להריץ שוב

```powershell
# מול בסיס הנתונים המקומי, אחרי Seed. קורא בלבד; העדכון בתוך measure.sql מבוטל ב-ROLLBACK.
# Bypass מתיר את הסקריפט להרצה הזו בלבד: ברירת המחדל ב-Windows (Restricted) חוסמת סקריפטים
powershell -ExecutionPolicy Bypass -File docs\performance\measure.ps1 -Label after-fix
```

התוצאות נשמרות ב-`performance/results-<label>.json`, ותוכניות הריצה ב-`performance/plans/<label>/`.
